## 4. Последняя функция: поиск и обязательная локализация

В проверенной develop 11 языков: en, ru, de, fr, uk, es, pt-BR, it, pl, tr,
zh-Hans. Registry — источник списка, а не эта строка. `released: false` не
освобождает доступный язык от перевода новых текстов и поисковых синонимов.

PR #285 покрывает все 70 записей каталога упражнений, 18 элементов оборудования/
рукояток и 17 групп мышц словарями на всех 11 языках. Названия и альтернативы
работают независимо от языка интерфейса, локально без сервера. Примеры:
«бабочка», «молотки», «гравитон», «румынка», RDL, OHP, местные аналоги.
Поддержаны регистр/диакритика/пунктуация, части и перестановка слов,
кириллическая транслитерация, немецкие ae/oe/ue и ограниченные опечатки.
Точные названия/синонимы идут выше частичных, оборудования/мышц и опечаток.
Фильтры соединяются AND; равные результаты сохраняют порядок каталога.

Поиск подключён к Exercise Library, добавлению упражнений и выбору сохранённого
упражнения в статистике. Конкретные варианты и History не объединяются:
румынская и классическая тяга — разные записи. Поиск оборудования может дать
несколько подходящих упражнений. Goblet остаётся одним видимым пунктом с двумя
конкретными ID/инвентарями. Поисковые альтернативы не добавляются в persisted
legacyExerciseIds и не переписывают сохранённые имена/данные.

Ключевые файлы PR:

- `lib/i18n/search/{locale}.ts`, `aliases.ts`, `types.ts`, `engine.ts`;
- `lib/i18n/catalog.ts`, `components/ExercisePerformance.tsx`;
- `scripts/check-localization.cjs` и тесты поиска/интерфейса;
- правило в `AGENTS.md`, `docs/PRODUCT.md`, `docs/LOCALIZATION.md`,
  `docs/EXERCISE_LIBRARY.md`, запись в DECISIONS и ROADMAP.

Правило на будущее: любые app-controlled тексты (включая инструкции,
ошибки/повтор, accessibility, названия/описания оборудования и новых функций)
переводятся на все текущие языки в том же изменении. Новые поисковые элементы
получают естественные альтернативы на всех языках. Новый язык должен покрывать
уже существующий контент и поиск. Для письменностей вроде Devanagari не удалять
смысловые гласные/знаки только ради общей accent-insensitive нормализации. Проверки выводят пропущенные ID/языки; ключи,
параметры и plural forms тоже проверяются. Структурная полнота не является
независимой проверкой качества языка. Пользовательский текст и исторические
снимки сохраняются как введены.

Если Hindi и поиск сливаются параллельно, согласовать словарь hi и реестр ДО
финальных проверок объединённой ветки. Не отключать coverage check ради merge.
Версионные конфликты решать по правилу фактического номера PR.

## 5. Утверждённые правила работы и версий

- React Native + Expo + TypeScript. Сначала инспекция branch/status/diff/history,
  затем существующая реализация, минимальные изменения, релевантные проверки.
- Сохранять пользовательские несохранённые правки. Не работать прямо в main.
- Одна понятная задача — отдельная ветка/PR. Merge остаётся за владельцем,
  не включать автоматический merge только из слова «утверждаю».
- В этом чате владелец явно разрешил публикацию ветки поиска и создание PR #285.
  Это не разрешение публиковать приватные эталоны или секреты в public repo.
- PR после выполнения и проверок должен стать Ready for review. Не оставлять
  завершённую утверждённую задачу в Draft без объяснения.
- Версия определяется реальным номером PR: #98 → 0.0.98, #105 → видимая 0.1.05,
  #285 → 0.2.85. Package/Expo SemVer без ведущих нулей. Сначала draft PR с реальным
  номером, затем `npm run version:pr -- N`, metadata commit, проверка, Ready.
  Коммиты того же PR версию не увеличивают. Схемы данных/native IDs не менять.
- Node 22.16.0 (сверить .nvmrc), npm 10.9.2; команды из актуального package.json.
  Обычно `npm ci`, `npm run check`, `npm run export:check`.
- Не объявлять JS export физическим тестом, веб-превью — Expo Go, выбор
  изображения — полным biomechanical QA, локальный ZIP — verified cloud backup.
- Если CLI Git не авторизован, использовать подключённый GitHub. При API-записи
  проверять соответствие дерева локально проверенному дереву. Не пересоздавать
  работу только из-за отсутствия CLI credentials.
- Общаться по-русски, коротко и конкретно; статусы и риски честно. Не задавать
  повторные вопросы на уже утверждённое. Разумные обратимые шаги выполнять.

## 6. Продукт и гарантии данных

CRESUM ранее назывался FitFlow. Стартовый релиз бесплатный, без рекламы и подписок.
Core: onboarding → Home → workout → упражнение → подходы → отдых → finish →
History → Progress. Offline-first; аккаунт не должен блокировать тренировку.

Нельзя терять активную тренировку/подходы, дублировать completed workouts,
переписывать стабильные exercise IDs или имена/значения исторических снимков,
смешивать разные варианты в силовых рекордах, сбрасывать введённый вес/повторы.
Перестройка каталога/иллюстраций не является миграцией истории.

Сохранять legacy storage/install identifiers, например fitflow_state_v1 и
com.fitflow.app, согласно REBRANDING.md; ребрендинг не означает заменить все
старые строки. Sign Out сохраняет местные тренировки. Импорт/экспорт, backup,
restore и recovery имеют собственные контракты, их не ломать новой функцией.

Supabase/Postgres — направление аккаунта и completed-history sync. В коде уже
есть поздняя интеграция Enable/Resume, merge-before-push, provenance, конфликты,
паузирование и RPC; не повторять устаревшее «sync вообще не реализован» из раннего
Stage 1. Но это НЕ доказательство, что текущие внешние сервисы/SMTP/rollout готовы.
Активная тренировка остаётся местной; реальные OTP/native/two-device acceptance,
домены/SMTP, public sharing/account-deletion gates и независимое восстановление
проверяются отдельно. Apple/Google auth не включать без отдельной задачи.

На будущее предусмотрены flags, capabilities/entitlements, admin, promotions,
rewards/referrals/badges. Это не текущий повод вводить платный Core или начинать
AI Coach, social, nutrition, wearables и постороннюю инфраструктуру.

## 8. Упражнения, инвентарь и изображения

- Мужской и женский утверждённые персонажи; выбор после установки и в Profile,
  хранится общим artworkModel; применяется к миниатюрам и фазам. Не показывать
  противоположную модель вместо отсутствующей и не менять ID упражнения.
- Новое упражнение/конкретный вариант с другой ручкой готовить сразу для Male
  START/FINISH и Female START/FINISH. Полная база развивалась поэтапно; цифру
  coverage сверять с текущим registry, не путать число изображений/пар/упражнений.
- START/FINISH генерировать одной согласованной парой, без надписей в финале,
  одинаково крупно и с полезным использованием кадра. Сохранять геометрию,
  хват, опоры, тросы и реальную механику; не дорисовывать случайные детали.
- Стиль оборудования сменён с раннего тёмного на светлый/серебристый; сохранять
  graphite кожухи/матовые тёмные подушки согласно референсу, а не белить всё.
  Единые кожа, одежда и материалы, без воска/пятен после серии редактирований.
- Для каждой генерации использовать настоящие эталоны персонажа/оборудования.
  Ссылки/названия файлов и предыдущие сгенерированные кадры не заменяют input image.
- Весь каталог оборудования доступен пользователю у каждого упражнения;
  по умолчанию выбрано то, что на принятой иллюстрации. Ручной выбор инвентаря
  сам по себе не превращает старую иллюстрацию в технически другой вариант.
- Goblet: dumbbell и kettlebell — два конкретных ID за одним видимым пунктом;
  статистика All/Dumbbell/Kettlebell сохраняет атрибуцию инвентаря.
- Admin/логотип на инвентаре: выбор групп/всего каталога, X/Y/Size 0–100 и
  «По умолчанию» восстанавливает утверждённую центрированную позицию.
- Muscle Map: отдельные передний/задний виды, слои/устойчивые ID, левая/правая
  стороны, мягкий красный, внешнее размытие отклонено. Выбран компактный вариант 3
  в карточке; различать Primary/Secondary и исследовательскую детализацию.
  SVG, анатомические границы и коэффициенты нагрузки нельзя «угадывать».
- Каждый новый/изменённый точный вариант проверять по EXERCISE_BIOMECHANICS,
  EXERCISE_ASSETS и данным каталога. Оригинальные описания, проверяемые источники;
  gymbot.ru — дополнительный discovery, не разрешение копировать материалы.
- Не делать ZIP после каждого упражнения. Оригиналы/промпты/провенанс сохранять,
  общий архив — в конце блока или по запросу. Ранее был запрос маленьких файлов
  до 1 МБ: выяснить актуальный контракт конкретного deliverable, не пережимать
  мастер-файлы без причины.

## 9. Отдельный визуальный workstream

Производственный контекст находится в отдельном приватном репозитории. Для

## 10. Oracle, Supabase и Expo Go: что переносится отдельно

По прежнему пользовательскому контексту работает Oracle preview и таймер
cresum-preview-update.timer с интервалом около 1 минуты после merge. Серверное
состояние в этой передаче не проверялось. Не выдавать этот факт за новый SSH audit.
Не менять нагрузку, firewall, systemd и не запускать streams/stress в рамках
переноса аккаунта. Проверять текущие unit files, ветку, HEAD, logs и доступы.

Expo SDK в текущем package: 58; пользователь просит Expo Go и предупреждать об

Oracle Object Storage cresum-visuals, eu-frankfurt-1 — отложенный приватный архив,
не активная обязательная зависимость приложения. Создание bucket не означает
подтверждённые upload/download и backup. Supabase и Oracle имеют разные роли.

## 12. Переход между аккаунтами и восстановление доступа

1. Создать проект CRESUM и загрузить этот документ. Project instructions взять
   из стартового сообщения выше, уточняя текущую задачу.
2. Подключить GitHub с разрешением работать с нужными репозиториями и проверить доступ к обоим репозиториям,
   включая приватный Visual Factory. Подключения/чаты/файлы старого аккаунта
   не считать автоматически доступными.
3. Скачать и прикрепить настоящие утверждённые визуальные эталоны и нужные
   оригиналы. Идентификатор файла из старого аккаунта не является самим файлом.
4. Для максимальной сохранности дополнительно сохранить релевантные старые чаты
   и вложения отдельным архивом. Если доступен экспорт данных, это дополнительный
   справочник; не рассчитывать, что он восстановит весь проект и все изображения.
5. Доступы к Oracle/Supabase/Expo восстанавливать штатно по мере задачи, секреты
   не включать в этот документ, публичный GitHub или разговор.
6. Перед уходом получить от нового ассистента короткую сверку: актуальные HEAD,
   статусы PR, число языков, ближайший шаг, список недоступных референсов.

## 13. Границы полноты этой передачи и provenance

Этот файл не содержит токенов/паролей, ключей, полного Git repository, всего
экспорта чатов, реальных серверных конфигов или всех оригиналов генераций.
Выбранные runtime assets остаются в GitHub; оригиналы/промпты нужно переносить
по их фактическому местонахождению. Старые приложенные AGENTS(1), PRODUCT(1),
DESIGN_SYSTEM(1), ROADMAP(1) не должны заменять более новые документы репозитория.

Утверждение в чате не равно merge; merge не равен deployment; зелёный CI не равен
визуальной/лингвистической проверке всех языков на телефоне. Не заполнять пробелы
выдуманными завершениями. Если конкретное старое решение не найдено — сначала
дочитать owning document/PR/исходную переписку, затем уточнить точный пробел.

В этом документе разделы о текущем HEAD, #285, инструментах и доступном коде
проверены по GitHub/репозиторию. Более широкие UX-пожелания и прежнее серверное
состояние перенесены из предоставленного контекста: они сохраняют согласованный
замысел, но не являются новой проверкой реализации. Если owning document, код и
этот снимок различаются — установить хронологию и источник, а не тихо менять
продукт. Полные прежние переписки в этом изменении не экспортировались.
